# Planner PWA — архитектура офлайн-режима

Подпроект внутри `plan/`: превращает существующий веб-планер (FastAPI + Jinja2 +
HTMX) в устанавливаемое приложение, которое работает без мобильного интернета и
при появлении связи сливает правки с сервером, не затирая чужие изменения.

Дата: 18.09.2026. Объём согласован с Верой: офлайн правятся задачи.

---

## 1. Задача и границы

Что решает подпроект:

1. Без сети добавлять, изменять и удалять **задачи**: название, описание,
   категория, приоритет, размер, дата, дедлайн, статус, «в бэклог», создание и
   закрытие подзадач, архив и восстановление.
2. Копить правки на устройстве и досылать их на сервер, когда связь появилась.
3. Показывать последние загруженные страницы без сети.
4. Ставиться на домашний экран Android как отдельное приложение.

Что НЕ входит (сознательно):

- Офлайн-правка остальных разделов: покупки, чтение, финансы, портфель,
  календарь, менеджеры, категории. Их формы без сети не выполняются — плашка
  прямо сообщает об этом, вместо того чтобы молча гасить нажатие.
- Push-уведомления и фоновая синхронизация при закрытом приложении.
- Одновременная работа двух устройств над одной задачей в реальном времени:
  телефон и компьютер догоняют друг друга при следующем обмене (см. раздел 5).

## 2. Из чего состоит

| Компонент | Файл | Ответственность |
|---|---|---|
| Service worker | `pwa/sw.js` | Кэш статики, страниц и JSON; офлайн-заглушки |
| Клиентский слой | `pwa/offline.js` | Срез задач, очередь правок, слияние, плашка, разбор конфликтов |
| Офлайн-страница | `pwa/offline.html` | «Нет сети» + список сохранённых страниц |
| Манифест | `app/web/static/manifest.json` | Установка на домашний экран |
| Отдача файлов | `app/main.py` | Роут `GET /sw.js` (с `Service-Worker-Allowed: /`) и монтирование `/pwa` |
| Публичные пути | `app/auth.py` | `/pwa` и `/sw.js` без токена — иначе воркер не зарегистрируется |
| API синхронизации | `app/api/offline.py` | `state`, `sync`, `conflicts` |
| Слияние | `app/services/offline_sync_service.py` | Применение действий, конфликты, журнал |
| Хранение | `app/models/offline.py`, `alembic/versions/011_offline_sync.py` | `offline_actions`, `offline_conflicts` |

## 3. Service worker

Версия кэша — константа `VERSION` в `pwa/sw.js`. Смена версии сбрасывает кэши
при активации; в плашке появляется «Обновить».

| Тип запроса | Стратегия | Кэш | Офлайн-ответ |
|---|---|---|---|
| Навигация (HTML) | network-first | `pages` | страница `offline.html` |
| Прочие GET (HTMX-фрагменты) | network-first | `pages` | короткая вставка «эти данные не сохранены» |
| `/api/*` GET | network-first | `data` | 503 (клиент это понимает) |
| `/web/static/*`, `/pwa/*`, `/uploads/*` | stale-while-revalidate | `static` | из кэша |
| `/login`, `/logout`, любой `?token=` | только сеть | — | — |
| POST/PUT/DELETE | не перехватывается | — | очередь в `offline.js` |

Решения, которые легко сделать неправильно:

- **Ответы сервера идут с `Cache-Control: no-cache, no-store`.** Cache API
  отклоняет запись таких ответов, поэтому перед `cache.put` тело пересобирается
  в новый `Response`, из заголовков остаётся `content-type`. Без этого кэш молча
  остался бы пустым.
- **Редирект на `/login` не кэшируется** (`response.redirected`): иначе под
  ключом главной сохранилась бы страница входа и офлайн показывал бы форму
  логина вместо задач.
- **Для HTMX-фрагмента отдаётся короткая вставка, а не целая страница.** Полный
  HTML-документ, вставленный в блок задач, ломает вёрстку. Статус — 200: на
  не-2xx htmx по умолчанию ничего не подменяет, и нажатие выглядело бы
  «ничего не произошло».
- **POST не перехватывается воркером**: подмена ответа ломает разбор ответа
  htmx. Офлайн-постановка в очередь живёт в клиентском слое.

## 4. Срез задач (база для слияния)

`GET /api/offline/state` отдаёт активные задачи и сохраняется в IndexedDB
(хранилище `state`). Этот срез — «то, что телефон знает о сервере». Он же
переиспользуется как страница данных без сети и обновляется после каждой
успешной синхронизации (ответ `sync` содержит актуальное состояние затронутых
задач).

## 5. Очередь правок и слияние

Хранилище: IndexedDB `planner-offline` (версия 2), хранилище `outbox`.

Запись очереди:

| Поле | Значение |
|---|---|
| `client_uuid` | ключ идемпотентности на сервере |
| `kind` | `create_task`, `create_subtask`, `update_fields`, `complete`, `uncomplete`, `archive`, `unarchive`, `to_backlog`, `delete_subtask` |
| `task_id` | id задачи (для создания — null) |
| `payload` | для `update_fields` — список `{field, from, to}` |
| `attempts`, `failed` | попытки и признак «повторять бессмысленно» |
| `created_at`, `title` | время постановки и подпись для интерфейса |

Ключевая идея слияния: в каждой правке поля хранится **не только новое значение,
но и то, каким поле было** (`from` — из среза задач на момент правки). При
досылке сервер сравнивает:

- поле на сервере всё ещё равно `from` → правка применяется;
- поле уже другое → создаётся запись в `offline_conflicts`, поле остаётся
  серверным, в плашке появляется «Разобрать (N)»: Вера видит оба значения
  («на сервере 20.09 / у тебя 25.09») и выбирает, что оставить.

Отсюда два следствия, ради которых всё делалось:

- разные поля, изменённые на телефоне и на компьютере, съезжаются оба;
- спор по одному полю не теряет ни одну сторону — ни молчаливой перезаписи, ни
  молчаливой потери офлайн-работы.

Дополнительно: каждое применённое действие пишется в `offline_actions` с
уникальным `client_uuid`. Повторная досылка (потерянный ответ, повторное
«Повторить») получает ответ `duplicate` и не создаёт дубль задачи.

Перехват форм — три барьера, и ни один не гасит событие «в пустоту»:

1. `submit` в capture-фазе: офлайн-форма раздела «Задачи» уходит в очередь до
   того, как её увидит htmx.
2. `htmx:beforeRequest`: страховка для кнопок с `hx-delete`/`hx-post`, которые не
   идут через `submit`.
3. `htmx:sendError`: запрос ушёл и не дошёл — ставим в очередь, только если
   `navigator.onLine === false` (иначе возможен дубль).

Если форма офлайн не поддерживается (покупки, финансы, категории), событие тоже
гасится, но с сообщением «Без интернета это действие недоступно» — потерять
действие молча нельзя.

Досылка — одной пачкой `POST /api/offline/sync`, ответ по каждому действию:

- `applied` / `duplicate` / `conflict` → запись удаляется из очереди;
- `rejected` / `error` → запись помечается `failed`, автоповторы прекращаются,
  в плашке появляется «Повторить»;
- редирект на `/login` (`redirect: 'manual'`, `opaqueredirect` или 401) → ничего
  не удаляется, плашка говорит «Нужно снова войти в планер, потом нажать
  „Повторить“». Это отдельный случай: раньше запись удалялась как успешная, и
  задача пропадала без следа;
- 5xx и сетевые ошибки → записи остаются, попытка повторится.

Запуск синхронизации: событие `online`, возврат вкладки в фокус, интервал 30
секунд и загрузка страницы.

## 6. Идемпотентность и целостность на сервере

- `offline_actions.client_uuid` — уникальный индекс. Повторная досылка не
  создаёт дубль и не применяет правку дважды.
- Каждое действие коммитится отдельно: одно битое не откатывает остальные из
  пачки (проверено тестом `test_broken_action_does_not_block_the_rest`).
- Значения полей сравниваются в нормализованном виде (дата → `ГГГГ-ММ-ДД`,
  пусто → пустая строка), поэтому «та же дата, записанная по-другому» не
  выглядит как конфликт.

## 7. Интерфейс состояния

Плашка внизу экрана (класс `.offline-bar`, стили в `app/web/static/css/style.css`):

| Состояние | Текст |
|---|---|
| Нет сети, очередь пуста | «Нет сети. Показаны последние загруженные данные.» |
| Нет сети, очередь N | «Нет сети. Ждут отправки: N.» |
| Сеть есть, идёт отправка | «Отправляю: N…» |
| Нужен вход | «Нужно снова войти в планер, потом нажать „Повторить“.» |
| Ошибка данных | «Не отправлено: N. Нажмите „Повторить“.» |
| Есть конфликты | «Не разобрано конфликтов: N.» + кнопка «Разобрать (N)» |
| Действие офлайн недоступно | «Без интернета это действие недоступно.» |

Добавленная офлайн задача сразу видна отдельной строкой с пометкой «в очереди»
(`.offline-draft`), правка существующей — пометкой `.offline-pending` на карточке.
Разбор конфликтов — модалка `.offline-modal` с двумя вариантами на каждое поле.

## 8. Ограничения и деградация

- **HTTPS обязателен.** Service worker регистрируется только в защищённом
  контексте: `https://` или `localhost`. По `http://<IP>` офлайна не будет.
- **Первый заход — только онлайн:** без него нет ни кэша страниц, ни среза задач.
- **Android может выгрузить кэш.** Офлайн-просмотр — «последние загруженные», а
  не полное зеркало.
- **Очередь живёт в браузере.** Очистка данных сайта уносит неотправленные
  правки; сервер об этом не знает.
- **Офлайн-вход невозможен:** кука проверяется сервером. Если сессия истекла,
  правки ждут в очереди до повторного входа.
- **Конфликт разрешает человек.** Автоматического «кто прав» нет по решению
  Веры: сервер не угадывает.

## 9. Как проверяется

Автотесты:

```bash
./.venv312/bin/python -m pytest tests/test_pwa_offline.py tests/test_offline_sync.py -q
```

`tests/test_pwa_offline.py`:
1. `GET /sw.js` — 200, `application/javascript`, `Service-Worker-Allowed: /`, без кэша.
2. `/pwa/offline.js` и `/pwa/offline.html` — 200 **без токена**.
3. Главная страница подключает `/pwa/offline.js`.
4. `GET /api/offline/state` возвращает срез задач.

`tests/test_offline_sync.py`:
1. Создание задачи офлайн (источник `offline`).
2. Повторная досылка — `duplicate`, в базе одна задача.
3. Правка названия офлайн при серверном переносе даты: применяется название,
   дата на сервере сохраняется (главный сценарий «не перетрёт»).
4. Правка одного поля с обеих сторон — конфликт: серверное значение на месте,
   запись в `offline_conflicts`.
5. Разрешение конфликта «поставить моё» — применяется локальное значение,
   конфликт закрывается.
6. Выполнение задачи — статус и архив.
7. Повторное выполнение — не ошибка.
8. «В бэклог» — дата снимается, счётчик переносов сбрасывается.
9. Неизвестное действие — `rejected`, без 500.
10. Битое действие не мешает остальным в пачке.

Ручной сценарий в браузере (Chrome DevTools → Network → Offline):

1. Открыть дашборд онлайн, дождаться регистрации service worker (DevTools →
   Application → Service Workers: activated).
2. Включить офлайн, перейти на `/` — страница отдаётся из кэша.
3. Добавить задачу — появляется строка «в очереди» и плашка.
4. Выключить офлайн — очередь уходит, задача появляется на сервере.
5. Спорный случай: изменить задачу офлайн и то же поле — в вебе; после
   синхронизации в плашке появится «Разобрать (N)».

## 10. Что дальше (вне этого этапа)

1. Офлайн-правка остальных разделов (покупки, чтение, финансы) — по тому же
   механизму слияния.
2. APK-обёртка (Capacitor): виджет на домашний экран, «поделиться в задачу»,
   локальные напоминания.
3. Локальная база задач вместо кэша страниц: мгновенный старт и полный список
   без сети.
